# 演示脚本（BeautyCare MVP）

> 所有测试人物与商品均为演示数据。虚构 SKU 带 `DEMO` 标识与 `is_demo=true`；
> 3 个真实 SKU 附实测抓取到的官方页面链接。品牌客服台、品牌需求面板与外发渠道均为本地模拟。

## 0. 准备

```bash
./scripts/bootstrap.sh          # 建库 + 迁移 + seed
cd frontend && pnpm install && pnpm build && cd ..
./scripts/run_server.sh         # http://127.0.0.1:8000
```

演示前请确认页面右上角的模式徽标显示 `MODEL=mock · WEATHER=mock · NOTIFICATION=in_app`，
并确认右侧「服务上下文」面板中的模型说明为 **mock 演示**。

演示身份：`consumer_a`（反馈积累充分）、`consumer_b`（反馈样本不足）、`staff`、`brand`。
页面提供明确标注的「演示身份」切换器（服务端固定映射，前端不提交任何 `user_id`）。

## 1. 已有产品 → 导入新品 → 确认入柜（US-01）

1. 以 **consumer_a** 进入 `/cabinet`：柜内已有 10 件产品，其中「澄泉深海修护精华」被标记为
   **待确认（无已审核资料）**。
2. 点击导入，选择 `data/fixtures/imports/demo_order_screenshot_1.png`。
   - 页面明确提示：当前为 **mock 模式**，只识别内置演示截图样本。
   - 识别得到 2 条候选：「轻透防晒乳 SPF50+ PA++++」「净澈去角质凝胶」，各带匹配理由与置信度。
3. **确认前**在 `/cabinet` 计数不变（对照测试 AC01）。
4. 把第 1 条名称改成「澄泉轻透防晒乳（已修正）」，数量确认为 1，点击确认 → 新增 2 件独立实例。
5. 再次上传同一张截图 → 提示「该文件此前已上传，未重复创建批次」。

要点：识别结果只是候选，必须用户确认；同用户同文件按内容哈希去重；截图在保留期后删除。

---

## 2. 新产品加入安排 → 生成草稿 → 接受为 v1（US-02 / AC04）

1. 进入 `/routine`，点击生成草稿（或在 `/chat` 说「帮我把这些产品安排成早晚流程」）。
2. 草稿卡片显示：步骤、时段、产品、说明、**每一步的依据与来源**、待确认产品列表、组合提示、不确定性。
   - 「澄泉深海修护精华」出现在**待确认列表**，没有步骤，也没有被编造频率或功效。
3. 接受草稿 → v1 生效；此前版本进入历史（若已存在）。

演示时点开任意步骤的「来源」：显示来源标题、定位、抓取/审核时间、是否虚构。

---

## 3. 组合适用性推理（US-12 / AC41 / AC42）

1. `/routine` 页面展示「组合提示」卡片，例如：
   > 这些产品含同类成分 Demo Clarify Acid。已审核资料说明：与含同类成分的产品叠加使用可能增加刺激风险，
   > 建议错开使用或降低使用频次。**系统不判定它们能否叠用**，请自行选择保留、间隔或移除其中一件。
2. 每条提示都列出引用来源，并提供三个选项：保留 / 间隔 / 移除其中一件。
3. 选择「间隔」→ 只生成**新草稿**，当前版本继续有效（`plan_changed=false`）。
4. 资料缺失的产品不参与组合推理（在待确认列表中）。

---

## 4. 步骤太多 → 保存偏好 → v2 差异 → 接受（US-03 / AC08）

1. `/chat` 说「现在步骤太多了，我只想保留三个步骤」。
2. 系统：
   - 保存偏好 `routine.max_steps=3`（出现记忆变更卡片）；
   - 直接生成 **3 步**草稿（偏好先于草稿生效）；
   - 展示相对 v1 的差异：新增/移除/调整，并说明「没有把两件产品合并成一步，也没有为凑数加入资料不足的产品」。
3. v1 在接受 v2 前继续有效；接受后 v1 进入历史。
4. 再次请求计划时不会重复询问步骤上限。

---

## 5. 记录使用问题（US-04 / AC09 / US-13 / AC43 / AC44）

1. `/chat` 说「昨晚用了澄泉光感精华之后有点刺痛」。
2. 系统保存为**用户报告的体验**（不是诊断结论），显示事件卡片与免责说明，
   并明确「不建议为了让系统确认而继续使用可疑产品」。
3. 因为该产品在当前计划中，系统生成**复核询问**：「是否要暂停该步骤？」（选项：暂停 / 保持 / 调整）
   —— 计划此刻**没有任何变化**（可切到 `/routine` 确认版本号不变）。
4. 选择「暂停」→ 生成 v+1 **草稿**（未生效）。切到 `/routine` 接受 → v+1 生效，原版本进入历史，
   反馈仍然保留在 `/memory`。

## 6. 成分图鉴（US-14 / AC45 / AC46 / AC48）

1. 以 **consumer_a** 打开 `/ingredients/atlas` 并点击生成。
2. 出现 4 张卡片（2 个正面高频、2 个负面高频），每张卡片包含：
   通俗名 + INCI 名、已知功效（附引用）、致敏性（附引用）、
   「你的反馈中，含此成分的产品出现了 N 次负面体验」、生活场景延伸（附来源与「非个人诊断」标注）、
   不确定性说明、以及「此信息仅供日常参考，不替代专业建议」。
3. 页面下方「未展示的延伸主张」列出被丢弃的生活延伸及其原因（例如 `SOURCE_NOT_APPROVED`），
   并明确标注为**无已审核来源支持，因此不展示**。
4. 「样本不足」区域列出事件数不足 `ATLAS_MIN_EVENTS` 的成分（含计数与阈值）。
5. 切换为 **consumer_b**（只有 1 条反馈）→ 卡片为空，全部显示「样本不足」。
6. 演示无来源成分：给 consumer_a 添加「澄泉维C亮肤精华」并记录 3 条反馈后刷新图鉴，
   将看到「澄泉神秘提取物」卡片显示 **暂无充分信息**（不展示功效与致敏性），
   「澄泉琥珀活性物」显示 **信息存在冲突，待审核**（两份 approved 来源互相冲突，不选边）。
7. 在卡片下「补充我的陈述」输入你的明确说法 → 写入 `IngredientFeedback`，与统计信号分开显示。

## 7. 图鉴删除联动（US-15 / AC47）

1. 在 `/memory` 删除一条负面反馈事件。
2. 返回 `/ingredients/atlas` 重新生成：该事件贡献的信号不再出现（计数下降或卡片消失）。
3. 刷新页面（模拟重启）：删除结果保持，被删事件不再进入上下文。

## 8. 连续客服交接（US-05 / AC16 / AC17）

1. `/service` 选择要包含的记录（产品、反馈、偏好），填写诉求，点击**预览**。
2. 预览草稿显示：包含的记录、已做动作、当前诉求、待确认事项；状态为 `draft`。
3. 点击确认提交 → 状态变为 `submitted`，`adapter_mode=local_demo`，`external_id=LOCAL-DEMO-…`，
   页面提示「已进入本地演示工作台，**未发送给任何品牌或外部客服系统**」。
4. 切换到 **staff** 身份打开 `/staff/tickets/:id`：页面顶部明确标注「模拟业务环境」；
   可以更新状态为 `resolved`、添加备注。
5. 切回 consumer_a，在 `/chat` 问「我上次那个工单现在怎么样了？」→ 系统返回**真实存储的状态与时间线**，
   不编造进度、不承诺结果。
6. 在 `/service` 确认「是否已解决」→ 该标记独立存储（客服标记 resolved 不等于用户确认解决）。

## 9. 实时环境与主动服务（US-07 ~ US-10 / AC23 ~ AC34）

1. `/environment` 手动选择「北京」（不使用 IP 推断），页面显示当前快照：
   provider、mode=mock、issued_at、valid_to、单位、quality、缺失字段。
2. 演示缺失字段：用 `POST /api/v1/admin/weather-scenario {"name":"missing_uv"}` 切换场景后刷新，
   UV 显示为**未知**（而不是 0）；切到 `stale` 显示已过时并暂停环境触发；
   切到 `api_failure` 显示提供方不可用（**不会**用 mock 数据伪装成实时数据）。
3. 创建行程「出差去北京」（24 小时后，目的地北京）。
4. `/settings` 授权「旅行提醒」、渠道勾选应用内、每日上限 3。
5. 触发调度：
   - 演示用：`curl -X POST http://127.0.0.1:8000/api/v1/admin/scheduler/tick -H "Authorization: Bearer <token>"`
   - 或等待常驻调度（每 60 秒）。
6. `/inbox` 出现「出行准备提醒（演示环境数据）」，包含触发原因、数据时间与来源、
   携带清单（逐条来自产品已审核资料）、以及稍后 / 无帮助 / 关闭此类。
   如果行程超出预报覆盖范围，页面显示**未知日期**。
7. 撤销「旅行提醒」授权 → 已排队但不再被授权的消息在发送前被取消（`/inbox` 不再出现新卡片）。
8. 取消行程 → 依赖它的待发消息立即取消。
9. 演示免打扰：把免打扰设为覆盖当前时间 → 决策变为 `defer`（`defer_until` 为免打扰结束后）；
   若延后已无意义则 `suppress`。每日上限达到后变为 `suppress`（原因 `DAILY_CAP_REACHED`）。
10. `/admin/proactive-decisions`（需 staff 或演示身份）可看到每条决策的 `reason_codes`、`rule_version`、
    环境快照 id 与引用，抑制原因可审计。

1. `/memory` 修改月度预算 300 → 500：新记录生效，旧记录标记为 `superseded`，只在历史中显示。

3. 以 consumer_a 访问 `/brand/insights` → 403（角色隔离）。

## 12. 数据导出与删除（AC22）

1. `/settings` 导出数据 → 返回完整 JSON（产品、计划、记忆、事件、工单、行程、图鉴）。
2. 删除账号数据 → 业务数据、上传文件与派生内容全部清除；共享产品目录与其他用户数据保留；
   页面说明「MVP 不保留备份副本，删除不可恢复」。

## 13. 演示重点（对应规格 17）

- 原本需要重复解释的信息能被**准确接续**（产品、反馈、计划版本、工单都在服务器侧）。
- 证据不足时系统会**停下来**：待确认列表、追问、`SOURCE_MISSING`、`暂无充分信息`、`样本不足`。
- 所有业务操作都有**真实可见状态**：草稿/生效/历史、工单状态与时间线、决策原因码、outbox 状态。
- 所有对外表述都标注 mock / 演示 / 本地模拟，不声称已连接真实品牌、订单、推送或原生 App。
